# Failure patterns learned from iterative figure work

These are general technical-illustration failure patterns. They describe observable mismatches, not proven explanations of a generation model's internal behavior. Examples are abstract and contain no project-specific evidence. Apply relevant cases rather than every restriction to every figure.

| Symptom | Failure mechanism or supported diagnosis | Prompt/design repair | Inspect in the output |
| --- | --- | --- | --- |
| Attractive diagram contradicts runtime | Modules were drawn without tracing calls and guards; parallel lanes implied concurrency | Derive a typed node/edge contract; distinguish list refinement from image-tensor flow | Execution order and the object on each edge |
| Disabled feature leads into rejection | Active and bypass paths shared crowded terminals | Use disconnected active/bypass panels with exact edge endpoints | Disabled/empty branches reach unchanged output |
| Supporting object looks like the removed object | A prohibition icon encoded the reference object rather than filter target | Show retained reference and rejected candidate separately, or use a neutral icon | Which object survives and which disappears |
| Layout percentages appear as performance metrics | Canvas allocation instructions leaked into visible text | Separate visible-label allowlist from construction; avoid numerical layout ratios unless needed | Every printed number has a valid source and meaning |
| Correct dimensions, incorrect crop or mask | Arithmetic labels were correct but scenes were redrawn or shapes approximated | Reuse one reference scene and coordinates; specify set subtraction, padding, clipping and scale; avoid duplicate inputs | Objects and geometry match, with no unexplained gaps or missing padding |
| Less processing implies merged outputs or huge speedup | Workload reduction was conflated with output identity, execution calls, or overall performance | Name the reduced unit; preserve output semantics; distinguish work count from latency | No unsupported speedup or change in output identity |
| Passing a filter looks like a confirmed event | Candidate-stage output was labeled as a final decision | Use the correct downstream label; retain additional decision stages when relevant | Output certainty matches implementation |
| Time alone appears to trigger an event | Timeline omitted the qualifying update at trigger time | Show both elapsed threshold and triggering observation; preserve exact inequalities | Trigger point includes all required conditions |
| Capability is shown as enabled deployment | Defaults, optional paths, user reports and observation were mixed | Label relevant configuration and evidence scope | No unverified current/latest/enabled claim |
| Clean image flows through painted annotations | Similar thumbnails were arranged as consecutive processing stages | Place clean input adjacent to model; separate annotation supervision route and disconnected legend | No solid dataflow through label artwork unless implemented |
| Scribbles resemble dense segmentation or decoration | Colored areas or tiny marks failed to communicate sparse labels | Sparse freehand strokes with matching wavy-line legend; explicitly show unlabeled areas | Strokes are class-specific; unmarked does not imply background |
| Local annotation classes imply global output classes | Local supervision and global prediction schemas were conflated | Check heads, losses, validity masks and configuration separately | Local legend does not change global output count |
| Realistic input represents the wrong thing | Whole-scene imagery stood in for a patch, or realism covered all modules | Specify viewpoint, object extent and processing unit; constrain realism to data interiors | Patch is local, correct target recognizable, modules readable |
| Gallery/training/model branches drift | Shared weights, normalization, caching or export boundaries were implicit | Label verified shared components and boundaries; separate preparation from per-query execution | No invented offline preprocessing or missing normalization boundary |
| File list implies build lineage | Observed names were connected without provenance evidence | Separate transformation procedure, observed inventory and proven mappings | No unsupported checkpoint-to-deployment identity |
| Whole set submitted before result review | Submission/download was treated as completion | Inspect a representative output before scaling, then review each image | Approval uses visible checks, not tool success |
| Captions appear out of order | Generation sequence became document numbering | Stable asset IDs plus a separate reading-order map | Captions start at 1 and cross-references agree |

## Structural acceptance precedes aesthetic acceptance

Use the checks that could change a reader's understanding:

1. **Semantics:** exact modules, roles, connections, gates, operations, units and output meaning.
2. **Representation:** correct input unit and target, consistent transformations, annotations separated from data.
3. **Communication:** readable labels at final size, unambiguous legend, no leaked instructions or invented metrics.
4. **Set/document consistency:** common style and terminology; reading order and cross-references.

Classify issues as required semantic fixes, communication improvements, or cosmetic preferences. A polished figure with a wrong branch remains unapproved. A correct schematic is not necessarily a pixel-accurate transformation.

After localized editing, check the defect and neighboring routes, then scan the full image for regressions. If a defect persists across repeated attempts, change layout or reduce scope rather than repeating the same request. Report the unresolved issue when the chosen method cannot satisfy it.
